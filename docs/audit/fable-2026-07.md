## Architecture

sqldeep transpiles a JSON5-like SQL DSL to standard SQL, ships a SQLite runtime function library, and provides Go/Swift/Kotlin bindings.

- **Core pipeline** (`dist/sqldeep.cpp`, ~1800 lines): pure string→string. `extern "C"` entry points (`sqldeep_transpile`/`_fk`/`_backend`/`_fk_backend`) → `transpile_impl()`. Flow: `lp_parse_all` (deepparser, a vendored fork of sqliteai/liteparser with sqldeep grammar extensions, `vendor/deepparser/src`, ~17k lines C incl. lemon-generated `parse.c`, arena allocator) → `Transformer::transform` (post-order in-place AST mutation) → `lp_ast_to_sql` (canonical unparser). Bare-expression inputs are wrapped as `SELECT <input>` and unwrapped on output.
- **Recursive rewrite**: `rewrite_recursive_select` builds a 3-CTE `WITH RECURSIVE` template **as SQL text by string concatenation** and **re-parses it** via `lp_parse` — an internal AST→text→re-parse boundary.
- **Runtime** (`dist/sqldeep_xml.c`, C): SQLite custom functions (`xml_element`/`xml_attrs`/`xml_agg` + `_jsonml`/`_jsx` variants, `sqldeep_json*`). All structured values returned as BLOBs; type discrimination by SQLite type + first byte. Escaping done via exact-length precomputation then manual buffer fill.
- **CLI** (`cmd/sqldeep.c`): `#include`s a patched vendored SQLite `shell.c` (`SQLDEEP_SHELL` hook in `shell_exec`); every SQL line is transpiled first, then the transpiled SQL is executed. Runtime installed process-wide via `sqlite3_auto_extension`.
- **Bindings**: `go/sqldeep` (cgo; `init()` calls `sqlite3_auto_extension`, so every go-sqlite3 connection in the process gets the runtime), Swift (pure-Swift runtime port + transpiler wrapper), Kotlin (JNI transpiler + pure-Kotlin runtime port).

## Invariants (audited)

The audit tracked 16 invariants. The confirmed findings violate:

- **#1 Semantic fidelity** — plain input must transpile to equivalent SQL or fail; violated by F3 (empty/clause-stripped success) and F4 (malformed JSON output).
- **#9 C API error contract** — no failure may return success; failure must be NULL + `err_msg`; violated by F3.
- **#10 SQL-text reinjection safety** — identifiers/literals spliced into the re-parsed RECURSE template must be quoted/escaped so crafted names cannot change template structure; violated by F1.
- **Trust-boundary #4 spirit / robustness** — runtime functions are callable from any SQL with attacker-chosen args and must not crash the host; violated by F2.

## Trust boundaries (relevant to confirmed findings)

- **#2 Transpiler output → live execution**: the CLI auto-executes transpiled SQL; binding callers execute the returned string with full connection authority. Any rewrite bug becomes executed SQL. (F1, F3, F4)
- **#3 AST → SQL text → re-parse in `rewrite_recursive_select`**: user-controlled identifiers and the unparsed WHERE clause cross from structured AST back into concatenated SQL text, only partially guarded. (F1)
- **#4 SQLite values → runtime functions**: `xml_element`/`xml_attrs`/`sqldeep_json_*` are ordinary registered functions callable from ANY SQL with attacker-chosen arguments (including nullable BLOB/column data). (F2)
- **#8 Process-global mutation**: Go `init()` and the CLI install the runtime via `sqlite3_auto_extension`, affecting every SQLite connection in the host process. Amplifies F2 into a process-wide DoS. (F2)

## Findings

### F1 — SQL injection / query-structure corruption via raw identifier splicing in `rewrite_recursive_select`

- **Severity**: High
- **Verdict**: CONFIRMED (reachability: confirmed; invariant-validity: confirmed)
- **Location**: `dist/sqldeep.cpp:1164` (also 1128, 1129, 1174, 1176, 1178, 1184, 1185, 1098, 1125-1126, 1139, 1143); re-parse at `:1204`; dispatch at `:550-551`
- **Invariant violated**: #10 (SQL-text reinjection safety); trust boundary #3
- **Failure scenario**: `rewrite_recursive_select` builds a `WITH RECURSIVE` template by string concatenation and re-parses it via `lp_parse`, splicing the RECURSE table name, `fk_col`, `pk_col`, projection field column names, and the `obj_pairs` column expression into that text **raw**. Identifiers arrive already dequoted (`liteparser.c:101` `lp_token_dequote` strips quotes/brackets and unescapes doubled quotes), and the unparser's normal `sql_ident`/`needs_quoting` guard (`lp_unparse.c:41-67`) is bypassed on this hand-built path. A quoted identifier carrying SQL structure therefore re-parses into a different query, which is handed back and executed with full connection authority (trust boundary #2). A legitimately quoted identifier with a space (e.g. `FROM "order items"`) also fails to round-trip.
- **Evidence**: Empirical exploit against `libsqldeep.a`:
  `sqldeep_transpile("SELECT { id, name, children: * } FROM \"t WHERE 1=1) SELECT secret FROM users;--\" RECURSE ON (parent_id)")`
  → `WITH RECURSIVE _sdq_dfs(...) AS (SELECT id, name, parent_id, 0, printf('%010d', id) FROM t WHERE 1 = 1) SELECT secret FROM users` — an attacker-chosen valid statement. Dequote at `vendor/deepparser/src/liteparser.c:101-138` (via `resolve_nm_dbnm` 84-87, `lp_make_from_table` 338); bypassed guard at `vendor/deepparser/src/lp_unparse.c:41-67`. (Note: the literal `--`-only payload and the benign `order items` case actually throw a parse error because the table name is spliced at two sites, so those specific sub-claims overstate; a crafted payload nonetheless achieves a clean valid injection.)
- **Fix sketch**: Never splice bare identifiers into the re-parsed template. Either (a) run every identifier through the unparser's quoting (`sql_ident`/`needs_quoting` — double-quote with embedded `"` doubled) before concatenation, or preferably (b) build the 3-CTE AST directly via `make_from_table`/`make_column_ref` etc. so identifiers are re-emitted by the trusted unparser instead of by string concatenation + re-parse.
- **Verification step**: Add a transpile golden test with a table/fk/pk/field identifier containing a space, a double-quote, a keyword, and SQL-structural bytes; assert the transpiled SQL round-trips the identifier verbatim (quoted) and that a structural payload does not alter the CTE shape. Confirm `FROM "order items"` maps to `FROM "order items"`, not `FROM order items`.

### F2 — NULL tag/name/key argument to XML & JSON runtime functions dereferences NULL → process crash

- **Severity**: High
- **Verdict**: CONFIRMED (both duplicate reports confirmed on both lenses)
- **Location**: `dist/sqldeep_xml.c:119` (also `:64`, `:68`, `:78`, `:90`, `:308-309`, `:352-353`, `:502-503`, `:532`, `:639-640`, `:654-655`); reachable from DSL via `dist/sqldeep.cpp:799-803` (`rewrite_object` computed key)
- **Invariant violated**: trust boundary #4 (runtime functions callable from any SQL with attacker-chosen args); invariant #9 spirit (errors must surface, not crash); #8 (JSON well-formedness)
- **Failure scenario**: `sd_xml_element` does `strlen(sqlite3_value_text(argv[0]))` with no NULL check; `sqlite3_value_text()` returns NULL for a SQL-NULL value, so `strlen`/`memcpy` dereferences NULL. The same unguarded pattern exists for every tag/name/key slot across the XML and JSON runtime functions. Existing NULL guards protect only the *value* operand, never the name/tag/key — so this is an omission, not a deliberate contract. Because the runtime is installed process-wide via `sqlite3_auto_extension` (Go `init()` and CLI), a single NULL in a tag/name/key slot on ANY connection crashes the entire host process — a remote-triggerable DoS from ordinary nullable data.
- **Evidence**: Reproduced SIGSEGV (exit 139) in the shipped CLI and in harnesses linking the cited object files: `SELECT xml_element(NULL)`, `SELECT xml_attrs(NULL,'v')`, `SELECT sqldeep_json_object(NULL,1)`, `SELECT xml_element_jsonml(NULL)`, `SELECT xml_attrs_jsonml(NULL,'v')`, `SELECT xml_attrs_jsx(NULL,'v')`. Pure-DSL reachability: `SELECT {(NULL): 1};` and the fully data-driven `CREATE TABLE t(k TEXT,v INT); INSERT INTO t VALUES(NULL,1); SELECT {(k): v} FROM t;` both exit 139, while the non-NULL control returns `{"a":1}` and exits 0 (`rewrite_object` key_form 3 passes the computed key straight to `sqldeep_json_object`). Realistic runtime path `WITH t(x) AS (VALUES('a'),(NULL)) SELECT xml_element(x) FROM t` also exits 139. Process-wide registration at `go/sqldeep/sqldeep_auto.c:14` and `cmd/sqldeep.c:21`.
- **Fix sketch**: In every runtime function, check `sqlite3_value_type(...) == SQLITE_NULL` (or a NULL `sqlite3_value_text` result) for tag/name/key arguments and either `sqlite3_result_error(ctx, "...NULL tag/key", -1)` or skip the pair, mirroring the existing NULL-value skip. A `safe_text(v)` helper returning `""` for NULL covers name/tag/key reads. Apply the identical guard to the Swift and Kotlin runtime ports for cross-binding parity (invariant #13).
- **Verification step**: Add `testdata/sqlite.yaml` cases feeding SQL NULL into the tag/name/key slot of each affected function (direct and via a nullable column and via the computed-object-key DSL form); assert a graceful SQL error or defined output and process survival, and run them across all six drivers (C++, Go, Swift macOS/iOS, Kotlin JVM/Android) so the ports stay in parity.

### F3 — Bare-expression fallback fails open: returns empty or clause-stripped SQL as success

- **Severity**: High
- **Verdict**: CONFIRMED (both duplicate reports — empty-return angle and clause-drop angle — confirmed on both lenses)
- **Location**: `dist/sqldeep.cpp:1647` (unwrap), `:1611` (bare-expr wrap), `:1662-1666` (multi-statement loop `if (sql) out += sql;`)
- **Invariant violated**: #1 (semantic fidelity), #9 (NULL + err on failure); trust boundary #2 (output is executed). Contract at `dist/sqldeep.h:39-40` ("On error returns NULL, sets err_msg/err_line/err_col").
- **Failure scenario**: `transpile_impl` wraps any statement-parse failure as `SELECT <input>` and, on the output side, unwraps only when the wrapped statement is exactly one `LP_STMT_SELECT` with one result column — extracting only that expression, with `out` left empty and returned as **success** when the shape check fails, and with any other clauses of the wrapped select silently discarded. There is no `else` branch and no error. The CLI `SQLDEEP_SHELL` hook (`vendor/src/shell.c:24639`) executes the non-NULL transpile result and returns, so SQLite's own syntax error is suppressed — a mistyped statement runs as a silent no-op. Binding callers execute an empty or clause-stripped statement with no error signal.
- **Evidence**: Reproduced against freshly compiled `dist/sqldeep.cpp` / `libsqldeep.a`:
  - `sqldeep_transpile("a, b")` → `""` (success, no error) — two result columns fail the `count == 1` unwrap.
  - `sqldeep_transpile("1, 2")` → `""` (success).
  - `sqldeep_transpile("1 UNION SELECT 2")` → `""` (success) — compound select fails the `LP_STMT_SELECT` kind test.
  - `sqldeep_transpile("x FROM t")` → `"x"` — FROM clause silently discarded.
  - CLI: `printf 'a, b;\n' | build/sqldeep` and `1, 2;` / `1 UNION SELECT 2;` produce no output, exit 0; `printf '1, 2;\nSELECT 99;\n' | build/sqldeep :memory:` prints only `99`. Controls `"a"`, `"a + b"`, `"SELECT 1"` transpile correctly.
  - The multi-statement loop's `if (sql) out += sql;` (`:1662-1666`) drops any statement whose `lp_ast_to_sql` returns NULL (OOM), producing a partial executed script — same fail-open shape, textually confirmed but only reachable under OOM (not demonstrated at runtime). The bare-expr path alone confirms the finding.
- **Fix sketch**: In the bare-expr output path, only unwrap when the wrapped statement is exactly one `LP_STMT_SELECT` with one result column AND no from/where/group_by/having/order_by/limit/with/compound structure; otherwise re-throw the ORIGINAL parse error (`parse_err` from the first `lp_parse_all`). Never return an empty string for non-empty input — treat `out.empty() && !input.empty()` as an internal error. Treat `lp_ast_to_sql` returning NULL as a hard `Error("internal: unparse failed")` in both branches instead of skipping.
- **Verification step**: Golden tests asserting that `a, b`, `1, 2`, `1 UNION SELECT 2`, and `x FROM t` each produce a transpile *error* (NULL return + `err_msg`), not empty/partial success; plus a CLI smoke test that a mistyped statement surfaces a syntax error rather than a silent exit-0 no-op.

### F4 — RECURSE DFS sort key `printf('%010d', pk)` produces malformed / mis-nested JSON for negative, >10-digit, or non-integer PKs

- **Severity**: High
- **Verdict**: CONFIRMED (reachability: confirmed; invariant-validity: confirmed)
- **Location**: `dist/sqldeep.cpp:1138` (also 1139-1143 path segment; 1183-1187 numeric `_child_rank`; 1198 lexicographic `ORDER BY _sort_key`)
- **Invariant violated**: #1 (documented DSL semantics); trust boundary #2 (rewrite bug becomes executed SQL / returned data)
- **Failure scenario**: The 3-CTE template orders event fragments lexicographically by a path built from `printf('%010d', pk)`, while comma placement uses numeric `ROW_NUMBER() OVER (PARTITION BY fk ORDER BY pk)`. Whenever lexicographic order of the padded string disagrees with numeric order, the rank-1 (no-comma) fragment is emitted out of position and the JSON is structurally corrupt — silently, with the query succeeding.
- **Evidence**: Reproduced against `build/sqldeep` on `:memory:`; all outputs fail `json.loads` while the query exits 0:
  - **Negative ids** (-2 root, children -1/-3): `[{"id":-2,"children":[,{"id":-1,...}{"id":-3,...}]}]` — `-000000001` < `-000000003` lexicographically but -3 is numerically first; leading comma + missing comma.
  - **>10-digit ids** (2000000000 and 10000000001, any snowflake-style 64-bit id): `[...,"children":[,{"id":10000000001,...}{"id":2000000000,...}]]` — 11-digit value overflows the 10-char pad, breaking alignment.
  - **TEXT pks**: `printf('%d','kid1')` = 0, so every sibling's key collapses to `0000000000` and `kid2`'s subtree mis-nests inside `kid1`. (STABILITY.md:272 documents "integer PKs only" as a current RECURSE limitation, so this sub-case is out-of-contract — but it corrupts silently rather than being rejected.)
  - Control with small positive integer ids produces valid JSON, isolating the sort-key construction as the cause. RECURSE is a documented feature (`dist/sqldeep-agents-guide.md:189-191`, `README.md:167-185`) marked Experimental in STABILITY.md.
- **Fix sketch**: Make the per-level sort component collision-free and order-consistent with `_child_rank`: use `printf('%019d', _child_rank)` (the `ROW_NUMBER` already computed per parent) instead of the raw pk for the path segment — rank is small, positive, and by construction matches the comma logic for every pk type. Requires computing rank before/inside the recursive CTE (seed `_path` from a ranked anchor and extend with the child's rank), or a second ranked pass that rebuilds paths from ranks. Additionally reject non-integer PKs explicitly rather than silently corrupting.
- **Verification step**: Add `testdata/sqlite.yaml` RECURSE cases with negative integer PKs, >10-digit (64-bit) PKs, and TEXT PKs; assert each output parses as JSON with correct sibling ordering and nesting, and run across all six drivers. Add a guard test that a non-integer PK yields a defined error, not silent corruption.

#### FO1 — Heap buffer overflow in `sd_xml_attrs`: under-counted attribute length

- **Severity**: High · **Verdict**: FINDER-ONLY (two-lens verification throttled)
- **Location**: `dist/sqldeep_xml.c:70` (length pass); structural writes at `:94`, `:95`, `:105`; `xml_escaped_len` at `:22-33`; `&quot;` expansion at `:98`
- **Invariant violated**: #5 (precomputed length must ≥ bytes written); #6 (attribute-context escaping)
- **Failure scenario**: The length pass reserves `2 + xml_escaped_len(val)` per attribute (`:70`), but the fill pass writes **three** structural bytes — `=` (`:94`), opening `"` (`:95`), closing `"` (`:105`) — under-reserving 1 byte per attribute, and `out[pos]='\0'` (`:107`) writes one past. Independently, `xml_escaped_len` (`:22-33`) has no `case '"'`, counting each quote as 1 byte, while the fill pass expands `'"'` → `&quot;` (`:98`, 6 bytes), under-reserving 5 bytes per quote in the value. Reachable from any transpiled `<t a="…"/>` over attacker-controlled DB text (trust boundary #3); attacker controls both quote count and attribute count, so the overflow length is arbitrary — heap-corruption / RCE-class primitive.
- **Evidence**: Static re-read during synthesis confirms the arithmetic: line 70 reserves `2 +` while the fill writes 3 structural bytes (`:94/:95/:105`) plus the NUL (`:107`); `xml_escaped_len` lacks a `'"'` case yet the fill emits `&quot;` (`:98`). `xml_attrs('a','x')` over-writes by 1 (structural + NUL); `xml_attrs('a','"""')` over-writes by ~3·5 + 1 + 1. **Not** dynamically reproduced (verification throttled).
- **Fix sketch**: Add `case '"': n += 6; break;` to `xml_escaped_len` (or a dedicated `xml_attr_escaped_len`) and change the `:70` reservation from `2 +` to `3 +` (space is already counted at `:67`). Verify reserved == written exactly against the fill pass.
- **Verification step**: Run the two-lens verifier; add a fuzz/golden case asserting the reserved length equals bytes written for attribute values containing `"`, `<`, `>`, `&`, and run under ASan.

#### FO2 — Aggregate append ignores `sqlite3_realloc` failure (NULL deref + leak) and int-overflows capacity math

- **Severity**: High · **Verdict**: FINDER-ONLY (two-lens verification throttled)
- **Location**: `dist/sqldeep_xml.c:201-209` (`xml_agg_append`); identical inline pattern at `:444-451` (`sd_jsonml_agg_step`) and `:702-707` (`sd_json_group_array_step`)
- **Invariant violated**: #14 (aggregate buffer growth must handle realloc failure without NULL deref; no write past capacity)
- **Failure scenario**: `p->buf = sqlite3_realloc(p->buf, newcap); p->cap = newcap;` then unconditional `memcpy(p->buf + p->len, …)`. (1) On realloc failure (heap/`soft_heap_limit`/OOM) the return is NULL, the old buffer leaks, `p->cap` is falsely advanced, and the memcpy writes through NULL+len → SIGSEGV in the host process holding the connection. (2) `int newcap = (p->cap + n) * 2 + 64` overflows `int` once the accumulated aggregate nears ~1 GiB (legal under `SQLITE_MAX_LENGTH`'s 1e9 default); `newcap` goes negative, `sqlite3_realloc(p, ≤0)` frees and returns NULL → same NULL memcpy, with corrupted negative `p->cap` persisting across later `xStep` calls. `SELECT xml_agg(big_col) FROM big_table` is a data-volume DoS.
- **Evidence**: Finder-reported; textual pattern present at all three cited sites. **Not** two-lens verified (throttled).
- **Fix sketch**: Compute `newcap` with `sqlite3_int64`/overflow-checked arithmetic, cap at `SQLITE_MAX_LENGTH` (→ `sqlite3_result_error_toobig`); realloc into a temp: `char *nb = sqlite3_realloc64(p->buf, newcap); if (!nb) { sqlite3_free(p->buf); p->buf = NULL; p->cap = p->len = 0; sqlite3_result_error_nomem(ctx); return; }`; make `xml_agg_append` return a status and have callers abort the step. Factor the three sites into one helper.
- **Verification step**: Run the two-lens verifier; add an OOM-injection test (allocator stub) plus a large-aggregate capacity-overflow test under ASan across the C, Go, Swift, Kotlin runtimes.

#### FO3 — NULL `input` pointer constructs `std::string(nullptr)` — undefined behaviour / crash

- **Severity**: High · **Verdict**: FINDER-ONLY (two-lens verification throttled)
- **Location**: `dist/sqldeep.cpp:1776` (`sqldeep_transpile_backend`); also `:1790` (`_fk_backend`), reached from `sqldeep_transpile` via `:1760`
- **Invariant violated**: trust boundary #1 (C API must survive malformed/NULL input without UB)
- **Failure scenario**: The caller-supplied `const char* input` is passed straight into `sqldeep::transpile(input, …)`, constructing a `std::string` from it. `std::string(nullptr)` is UB (libc++ calls `strlen(NULL)`) → segfault. No NULL guard exists on the input path; trust boundary #1 explicitly requires surviving NULL input.
- **Evidence**: Finder-reported; no guard visible at the cited entry points. **Not** two-lens verified (throttled).
- **Fix sketch**: At each `extern "C"` entry: `if (!input) { set_error(…, Error("input is NULL", 0, 0)); return nullptr; }` before constructing the `std::string`.
- **Verification step**: Run the two-lens verifier; add a C-API unit test passing `NULL` to each entry point, asserting NULL return + `err_msg` and process survival.

#### FO4 — Non-`sqldeep::Error` C++ exceptions escape the `extern "C"`/FFI boundary → host termination

- **Severity**: High · **Verdict**: FINDER-ONLY (two-lens verification throttled)
- **Location**: `dist/sqldeep.cpp:1777` (and `:1791`); interior `catch (...)` rethrow at `:1641`
- **Invariant violated**: #8 (no C++ exception may cross the `extern "C"`/cgo/JNI/Swift boundary)
- **Failure scenario**: `transpile_impl` uses `std::string`/`std::vector`/`std::map`/`std::sort`/`std::to_string`, any of which can throw `std::bad_alloc` or `std::length_error` on large/adversarial input. The bridge only has `catch (const sqldeep::Error&)`; the interior `catch (...)` at `:1641` merely destroys the arena and rethrows. A `std::bad_alloc` therefore propagates out of an `extern "C"` function (and through cgo/JNI/Swift frames) — UB that terminates the whole host process instead of returning NULL + `err_msg`.
- **Evidence**: Finder-reported; the cited `catch` clauses match only `sqldeep::Error`. **Not** two-lens verified (throttled).
- **Fix sketch**: After `catch (const sqldeep::Error&)` in both `_backend` and `_fk_backend`, add `catch (const std::exception& e)` (generic `err_msg`, line/col 0) and a final `catch (...)`, converting every escape into the documented NULL-return + malloc'd `err_msg` contract.
- **Verification step**: Run the two-lens verifier; add a test that forces `std::bad_alloc`/`std::length_error` (allocator stub or oversized input) and asserts NULL + `err_msg`, not termination, across all FFI bindings.

#### FO5 — `Transformer` alias map never cleared: aliases leak across statements & sibling scopes

- **Severity**: High · **Verdict**: FINDER-ONLY (two-lens verification throttled)
- **Location**: `dist/sqldeep.cpp:329-331` (`transform()` builds `alias_map_` without clearing); `:1636-1639` (one `Transformer` reused for every statement); unknown-alias error at `:1283-1285`
- **Invariant violated**: #1 (semantic fidelity; also defeats the "unknown join alias" hard error and transform idempotency)
- **Failure scenario**: (a) **Cross-statement**: `SELECT * FROM customers c; SELECT * FROM c->orders o` — statement 2's alias `c` should throw "unknown join alias 'c'", but `alias_map_` still holds `c→customers` from statement 1, emitting a correlation to an alias absent from statement 2's scope. (b) **Sibling scopes**: `SELECT (SELECT … FROM customers c … FROM c->orders), (SELECT … FROM companies c …)` — the flat last-writer-wins prepass resolves `c` to `companies` for the first subquery; the join condition becomes `orders.companies_id = …` instead of `orders.customers_id = …`, silently returning wrong rows.
- **Evidence**: Finder-reported. **Not** two-lens verified (throttled).
- **Fix sketch**: Clear `alias_map_` at the top of `transform()` (fixes cross-statement leakage), or construct one `Transformer` per statement in `transpile_impl`. For intra-statement shadowing, scope the map per SELECT (push/pop a stack) or detect duplicate alias keys mapping to different tables and throw.
- **Verification step**: Run the two-lens verifier; add golden tests for the two-statement and sibling-scope cases asserting the correct error / correct FK column.

#### FO6 — `int` accumulator in `xml_escaped_len`/`json_escaped_len` overflows on ~GB input → heap buffer overflow

- **Severity**: High · **Verdict**: FINDER-ONLY (two-lens verification throttled)
- **Location**: `dist/sqldeep_xml.c:22` (`xml_escaped_len`), `:244`, `:636-664`, `:668-686` (`json_escaped_len`/`json_value_len`)
- **Invariant violated**: #5 (precomputed length ≥ bytes written); trust boundary #3 (runtime args are attacker-influenced DB content)
- **Failure scenario**: Length accumulates in `int`. `json_escaped_len` can add up to 6 bytes per input byte, `xml_escaped_len` up to 5. A large value (default `SQLITE_MAX_LENGTH` 1e9) of mostly control chars (~0.72e9 bytes of `0x01`) yields a true escaped length ~4.3e9, wrapping the 32-bit signed accumulator to a small positive. `sqldeep_json_object`/`_array`/`xml_*` then `sqlite3_malloc` that small size while the fill pass writes the full multi-GB expansion — heap overflow. Any SQL can trigger it (trust boundary #3).
- **Evidence**: Finder-reported. **Not** two-lens verified (throttled).
- **Fix sketch**: Compute lengths in `size_t`/`int64`; bail with `sqlite3_result_error_toobig` when the required size exceeds the `sqlite3_malloc` int limit, or cap input via `sqlite3_value_bytes` before the fill pass.
- **Verification step**: Run the two-lens verifier; add a large-control-char-input test under ASan asserting either a toobig error or a correctly sized allocation, across the C runtime (and Swift/Kotlin ports).
